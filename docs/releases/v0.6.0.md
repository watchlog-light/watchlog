# WatchLog 0.6.0

The release that carries WatchLog Cloud. The same product can now run as a hosted, multi-organization service (`WATCHLOG_EDITION=cloud`): sign-up, a setup wizard that connects a Kubernetes cluster or a Docker fleet in a couple of minutes, plans with limits, and the database itself keeping each organization's rows apart. Cloud opens as a beta, by invite from the waitlist, with Pro free during the beta ([WatchLog Cloud](https://github.com/watchlog-light/watchlog/blob/v0.6.0/docs/site/cloud.md)).

**Self-hosted installs don't change.** With `WATCHLOG_EDITION` unset (the default), none of the Cloud features exist: one organization, no limits, no sign-up, no billing, the first-run setup and invites as before. What self-hosters do get is listed under "For self-hosted installs" below.

## What's new in Cloud mode

Everything here is off unless `WATCHLOG_EDITION=cloud`; the Cloud routes answer 404 otherwise. The variables are in [configuration](https://github.com/watchlog-light/watchlog/blob/v0.6.0/docs/site/configuration.md#cloud-mode-watchlog_editioncloud).

- **Organizations kept apart by the database** (ADR-174): every tenant row carries its organization, and PostgreSQL's Row-Level Security enforces it under a request-path role that can't bypass it (`watchlog_app`); the backend refuses to start in Cloud when that role could. Queries to VictoriaMetrics need the organization's own cluster scope. A cross-organization suite calls every REST route, MCP tool, query and stream as one organization with another's ids, on every push (ADR-182).
- **Accounts** (ADR-175): sign-up with email and password (checked against known breaches with k-anonymity), GitHub or Google; email verification (you can start before you click the link, for 7 days); optional two-factor sign-in (TOTP, 10 recovery codes), required for the Owners of a paying organization; Cloudflare Turnstile on sign-up and reset; sessions you can list and end; one account in many organizations, with an organization switcher. Sign-up opens by invite, in waves, until staff open it to everyone.
- **The setup wizard** (ADR-176): Kubernetes or Docker, a name, one command (Helm, a `kubectl` manifest fetched with a one-time install code so the token never sits in a URL, `docker run` or a Compose service), then a live checklist as the agents report, the first metrics arrive, eBPF starts and the service map draws its first edge. After 2 minutes without an agent it shows what to check. A first-week card on the overview suggests the next steps.
- **Plans and limits** (ADR-177): Cloud Free (1 cluster or fleet, 5 nodes, 3 days of history, 1 user) and Cloud Pro (unlimited clusters and nodes, 30 days, up to 10 users). A limit never stops what already works: a second cluster or user answers 409 `plan-limit`, a new node beyond the plan gets 402 while the others keep sending, and a downgrade keeps everything sending for 14 days. Nodes are counted hourly and billed on the month's 95th percentile. Two VictoriaMetrics tiers (3 and 30 days), read together after a plan change.
- **Billing** (ADR-178) is a separate service behind an interface, built and tested against Stripe's test tooling only, with its live switch off: during the beta an Owner turns on Pro without a card, and gets 14 days' notice by email before billing starts. The product's side is Settings › Plan & billing and an internal API on its own listener.
- **Lifecycle emails, the funnel and the Cloud admin's API** (ADR-179): a few emails (welcome, no data yet, first alert, tips, near a limit) with one-click unsubscribe; funnel events; an internal admin API for staff (organizations, plans, invite waves, suspensions); **support sessions**, read-only for at most an hour, with every Owner emailed and each page opened listed in Settings › Security.
- **Data rights and the security baseline** (ADR-181): export of the configuration and of a cluster's metrics, deletion with a 7-day undo, inactive Free organizations warned and then suspended; a strict Content-Security-Policy and headers on the API and (with `WATCHLOG_EDITION=cloud` on the web container) the dashboard; alert channels may post only to public addresses, checked at save and at send; per-organization request, stream, series and query limits. An independent review against OWASP ASVS L2 ran before the release; its findings are fixed or recorded in the decisions.

## For self-hosted installs

- **Add cluster shows a live checklist** (ADR-176): under the install command, the page ticks as the agents report, the first metrics arrive, eBPF starts (or says why not, with the fix) and the service map gets its first edge. For Kubernetes clusters and Docker fleets; `GET /clusters/{id}/onboarding-status`, also as Server-Sent Events. The install commands themselves are 0.5.0's.
- **Lighter heartbeats:** an agent's and a cluster's "last seen" time is written at most once a minute instead of every 15 seconds; a new agent, or a changed mode, version or capabilities, still at once. Far less database write volume on large installs. An agent that stops now shows as silent 2 to 3 minutes after its last heartbeat (was 3 to 3¼).
- **Audit events record the visitor's address** from your trusted proxy's header (the same setting as rate limiting), not the proxy's own.
- **The request log** masks the tokens in reset and invite links and any `token=` value, as it already masked `code=`.
- The dashboard asks the server once, at load, whether it runs in Cloud mode; a self-hosted server answers 404 and nothing else changes.

## Fixed

- **An alert rule change with nothing in it** (an empty `PATCH /alert-rules/{id}`) answered 500; it answers the rule now.

## Upgrading

No manual steps (ADR-107). Kubernetes: `helm upgrade … --version 0.6.0 --reuse-values`. Docker: set `WATCHLOG_VERSION=0.6.0` and `docker compose pull && docker compose up -d` for the server. The Helm charts and the Compose file have no new values; agents and integrations collectors from 0.5.0 keep working, and there is nothing new in them to upgrade for.

**Migrations run by themselves.** There are eight, all forward-only; what each does to a self-hosted database:

- **Tenancy** (`1794700000000_tenancy-rls`): adds the organization column to the eleven tables that hung off a cluster or a parent row (objects, change markers, agents, cluster tokens, ingest errors, collectors, Kubernetes events, integration credentials, notification alerts, API token events, Telegram verifications), fills it from that parent, and adds composite foreign keys and Row-Level Security policies. Self-hosted servers keep connecting as the role that owns the tables (the one in `DATABASE_URL`, which ran the migrations), and RLS doesn't apply to a table's owner, so every row stays visible exactly as before; inserts fill the column from the parent by themselves. It rewrites those tables' rows once: under a second for 14,000 events and 3,900 objects; longer for very large event tables, before the backend starts.
- **Accounts** (`1794800000000_cloud-accounts`): new, empty tables for Cloud identities, verification links and recovery codes; nullable columns for two-factor sign-in on users and for a session's current organization on sessions (existing sessions stay signed in). A user's password becomes optional (for GitHub and Google accounts) and the unique email index covers accounts with a password: every self-hosted account has one, so the rule is the same.
- **Onboarding** (`1794900000000_cloud-onboarding`): two new, empty tables (install codes, the first-week card).
- **Entitlements** (`1795000000000_cloud-entitlements`): columns on the plan table, which a self-hosted server never fills (no row, no limits); two new, empty tables for limit hits and the hourly node count; one index on agents.
- **Funnel and support** (`1795100000000_cloud-funnel-support`): new, empty tables (funnel, lifecycle emails, support sessions); nullable columns for suspension and for unsubscribing; the audit and API-token event kinds gain Cloud's kinds, and existing rows keep theirs.
- **Data rights** (`1795200000000_cloud-data-rights`): nullable columns on organizations for deletion and inactivity, a new deletion record table, and Cloud's audit kinds.
- **Invite waves** (`1795300000000_cloud-signup-invites`): two new, empty tables (Cloud's settings and sign-up invites).
- **Two-factor lockout** (`1795400000000_cloud-mfa-lockout`): two columns on users that stay 0 and null without two-factor sign-in.

A server you upgrade keeps its organization, users, sessions, clusters, tokens, alert rules, channels, silences, applications and history.

**One case to check before upgrading:** if you run the backend against an external PostgreSQL where the tables belong to a different role than the one in `DATABASE_URL` (say, migrations run by hand as an admin role, and the backend on a role with grants only), Row-Level Security would hide the rows from that role. With the Helm chart and the Compose file the backend's role owns the tables (it runs the migrations), so nothing changes. If yours differs, run the backend as the owner, or give its role `BYPASSRLS`.

## Known limits

- Cloud is a beta: billing is built but off, and Stripe has been exercised with its test tooling only. Pro is free until billing starts, with 14 days' notice.
- Per-organization request limits are kept in memory, per backend process: Cloud runs one backend replica until they move to a shared store.
- On a self-hosted server, deleting a cluster keeps its metrics until retention removes them (Cloud deletes them with the cluster).
- The overview's charts can trail the live checklist by up to a minute after the first data, until the first full chart step.
- English only.
