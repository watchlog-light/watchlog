# WatchLog 0.3.0

Your databases, caches, queues and web servers, next to the cluster they run in. WatchLog 0.3 finds Redis, PostgreSQL, Nginx and RabbitMQ in what its agents already see, on Kubernetes clusters and Docker hosts. Press Monitor, and each gets its own page, the reasons behind a problem and default alerts. Your team can join too: Owners, Admins and Viewers.

## What's new

- **Applications** (ADR-131, ADR-132, ADR-135):
  - **Found by themselves:** services are discovered from images and ports. Press **Monitor**, or **Ignore** one or a whole namespace or Compose project.
  - **The integrations collector** reads them with read-only access: a Deployment in each cluster (in the chart, idle until a service is monitored) and one container per Docker host (the page shows the command).
  - **Every service page** has the type's own tabs, "What WatchLog sees" (each reason with its facts and the workloads or containers it points to), the workloads that connect to it, its alert rules, and reachability.
- **Redis and Valkey** ([guide](https://github.com/watchlog-light/watchlog/blob/v0.3.0/docs/site/integrations/redis.md)): memory against maxmemory, evictions, hit rate, the slow log, latency histogram, clients by workload, persistence and replication. Key values are never read.
- **PostgreSQL** ([guide](https://github.com/watchlog-light/watchlog/blob/v0.3.0/docs/site/integrations/postgres.md)): connections against max_connections and who holds them, the slowest queries (normalised; query text can be turned off), locks and the session blocking them, replication lag and slots, vacuum and wraparound, table and index sizes, capacity.
- **Nginx and ingress-nginx** ([guide](https://github.com/watchlog-light/watchlog/blob/v0.3.0/docs/site/integrations/nginx.md)): requests, 5xx and latency per upstream with nothing to set up (eBPF), error bursts marked "during rollout", upstreams without endpoints, connections from `stub_status` or ingress-nginx, expiring certificates. ingress-nginx serves its metrics only with `controller.metrics.enabled`; the page gives the command.
- **RabbitMQ** ([guide](https://github.com/watchlog-light/watchlog/blob/v0.3.0/docs/site/integrations/rabbitmq.md)): queues, consumers, message rates and node limits from the built-in prometheus plugin. When a queue grows with no consumers, WatchLog names the client that was connected to RabbitMQ and ended (OOM-killed, crash-looping, exited) around then.
- **Connecting** (ADR-133, ADR-134): for services that need a user, WatchLog writes the command that creates a read-only one, tests the login before you save, and says which tab needs which privilege. Passwords are stored encrypted, or stay in your own Secret or a file on the host.
- **HTTP on the service map** (ADR-139): requests per second, 4xx and 5xx, and p50/p95/p99 on every plain-HTTP edge, from the first 16 bytes of each message. No paths, headers or bodies; TLS is never decrypted. An edge with 5 % 5xx turns critical.
- **Alerts for services** (ADR-136, ADR-144): default rules per type, chosen in the Monitor drawer; any service metric in a custom rule; a rule can cover every service of a type.
- **Multi-user** (ADR-140): Owner, Admin and Viewer; invites by email or link; Viewers see everything and change nothing; API tokens follow their user's role.
- **MCP:** `list_applications` and `get_application`, with every reason in words and facts, and the services' metrics in `query_metric`.

## Security

- The collector runs only fixed, read-only statements and commands written in its code; nothing the backend sends is executed (ADR-131).
- Credentials are encrypted with the installation's key, sent only to the collector that needs them, and never shown again (ADR-133).
- PostgreSQL query text is normalised (no literals), utility statements keep only their command, and passwords are redacted; Redis credential commands keep only their name (ADR-138).
- eBPF HTTP reads 16 bytes per message and keeps only the method class, status code and timing ([what the agent can access](https://github.com/watchlog-light/watchlog/blob/v0.3.0/docs/site/security.md)).

## Upgrading

Upgrades need no manual steps. Migrations create the new tables; the 0.2 admin becomes the Owner. Every new chart value is optional: the integrations collector (`integrations.enabled`) and HTTP stats (`agent.networkFlows.http`) come on with `helm upgrade --reuse-values`.

- **Docker hosts:** to monitor services there, start the collector with the command on the service page. The agents work as before; re-run their install command for HTTP stats.
- **Kubernetes:** if you install from the chart with custom container ports, discovery now sees them (they were dropped before, so services were monitored on their type's default port).

## Known limits

- MongoDB comes in 0.3.1, Elasticsearch in 0.5.
- HTTP stats are HTTP/1.x in plain text; HTTP/2, gRPC and TLS show as connections only. On arm64 kernels before 6.0 they're off (no BPF trampolines), and the agent says so.
- One cluster per installation (Community). English only.
