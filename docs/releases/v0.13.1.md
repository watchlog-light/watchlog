# WatchLog 0.13.1: one list on the Scheduled jobs page

The Scheduled jobs page showed every job twice, once in a timeline and once in a table. Now
it's one list, each row with its run strip.

## What's new

- **Jobs and their runs:** one row per job: the job and where it runs, its schedule in words
  with the next run, the run strip (6 h, 24 h or 7 days), the last run ("Failed, exit 137 · 7 in
  a row") and its status. Rows go in one order: need attention, running, working, then the ones
  that haven't run yet. The "Last 14 runs" column is gone; a job's page keeps its run history.
- **Not running, out of the way:** disabled timers, cron lines on a server with no cron daemon
  and suspended CronJobs sit in one collapsed row ("3 not running: 2 disabled, 1 suspended"),
  each with its reason, and no longer count as needing attention.
- **Before WatchLog was watching:** the part of a strip before WatchLog first saw the job is
  hatched, so a blank strip on a new server no longer reads as "didn't run". A fleet or cluster
  watched for less than a day says for how long.
- **Schedules in words** for systemd timers as for cron: "Every hour at :09 and :39", "Every 2
  hours at :50, from 01:50", "Weekdays at 18:00". What can't be said shows as written; the
  expression as written is always in the tooltip.
- **Random delays and relative timers:** "next around 00:00 (up to 4 h later)" with a faint bar
  on the strip; a timer that runs after its last run gets its next time from that run.
- The range starts at 24 hours once for everyone, then the page remembers your choice again.

## Fixes

- A timer whose run was still going showed "no next run" in the timeline and a stale time in the
  table (systemd gives no next time until the run ends). One next-run answer now serves the
  list, a job's page, the Overview and the strip.

## Upgrading

No manual steps and no migration. Agents 0.13.1 report a relative timer's interval; older
agents keep working, and such timers show no next run until they're updated.
