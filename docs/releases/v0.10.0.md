# WatchLog 0.10.0: Certificates and scheduled jobs

Two things fail quietly until they hurt: a certificate that wasn't renewed, and a scheduled job
that stopped running or keeps failing. WatchLog now finds both by itself, on Linux servers and
on Kubernetes, and alerts before they become an outage. Nothing to configure. And every email
WatchLog sends now has one designed template.

## What's new

### Certificates

- **Found by the agent, from the server itself.** Every listening TCP port is asked for the
  certificate it presents, every 10 minutes, with STARTTLS on the mail and database ports
  (SMTP, IMAP, POP3, PostgreSQL, MySQL). The names in the server's certificate stores (Let's
  Encrypt, acme.sh, Caddy; only their directory names) are asked for one by one, so each
  virtual host's certificate is found.
- **On Kubernetes**, the cluster-agent reads each TLS Service at its cluster address (the API
  server's own certificate included) and each Ingress's TLS hosts on its controller's Service.
  It reads Ingresses' hosts only, never the Secret a TLS section names; the chart grants
  `get, list, watch` on Ingresses for it.
- **No traffic decrypted, no private key read**: WatchLog sees only what a client sees.
- **Renewals are tracked.** Every certificate seen under the same names is kept, so the tab
  says "renews itself; last time 32 days ago" once it has seen one, and names the job that
  renews it (certbot, acme.sh) when it sees that job, and when that job is failing.

### Scheduled jobs

- **systemd timers** from systemd itself: schedule, random delay, catch-up after a reboot, and
  each run of the unit it starts with its exit code.
- **cron jobs** from the crontabs on the server, matched with the processes cron really starts
  (a small eBPF program, filtered in the kernel to cron's children); without eBPF, from cron's
  text log, without exit codes.
- **Kubernetes CronJobs**: each Job a run, a failed pod's exit code, `spec.timeZone`.
- **States with their reasons:** Failing (exit code, how many times in a row, the last good
  run), Missed (a run was due and none started, told apart from the server being off or the
  agent stopped), Slow (3 times its usual duration), Running, Working. A random delay, a
  catch-up after a reboot and daylight saving changes are never "late".
- **Only a name leaves the server.** A cron job is named from its command (`pg_dump`,
  `artisan schedule:run`, `cron.daily`); its command line, arguments, environment and user
  never are. A crontab line with a password in it is tested.

### In the dashboard

- **Applications gets three tabs**: Services, Certificates and Scheduled jobs. Four tiles,
  problems first, filters, cards on phones, a certificate's page with its history and a job's
  page with its runs and, for a timer, its unit's log on demand.
- **The Overview and each server's page** show their counts and problems; **search** (⌘K)
  finds them by name.
- **Five default alerts**, in every edition and for both Kubernetes and servers: a
  certificate expiring (14 days warning, 3 days or expired critical), a certificate's name or
  chain wrong, a job failed (critical at 3 in a row; a job every few minutes only at 3), a job
  missed, a job slow. One alert per certificate or job, not per run.
- **Events** for a certificate renewed, expiring or expired, and a job failed, missed or
  recovered; **probable cause** names an expired or mismatched certificate where a failing
  connection arrives, and the failing timer behind a service that failed.
- **API and MCP:** read-only routes for both lists and each item, and the MCP tools
  `list_certificates` and `list_scheduled_jobs`.

### Emails

- **One designed template for every email**: sign-up, verification (now with a 6-digit code
  you can type where you are signed in), resets, invites, alerts, billing and the account
  emails. Readable in real mail clients at 320 px, light and dark, with no remote image or
  script, and a plain-text part ([ADR-220](https://github.com/watchlog-light/watchlog/blob/v0.10.0/docs/DECISIONS.md)).

## Changed

- **Alert email subjects.** `[CRITICAL] … (prod)` became `[Critical] … in prod`, and a server's
  alert says `on <server>` when its title doesn't name it. **If you filter alert emails by
  subject, update the filter.** A resolve, a reminder or an escalation threads under its alert.

## Measured

- **1,000 servers on WatchLog Cloud's kit for 10 minutes** (0.10 agents, each with 24 scheduled
  jobs and 3 certificates and a snapshot a minute): 14 inventory snapshots a second at p95
  61 ms, 67 writes a second at p95 23 ms, heartbeats at p95 11 ms; no request failed.
- **About 75 more series a server** (three a job, one or two a certificate), 13 to 15 % on
  top of a 0.9 server's.
- **The Servers end-to-end test** passes on Ubuntu 24.04, Debian 12 and Rocky 9 (55 checks
  each), with real nginx, systemd timers and cron; the upgrade from 0.9.10 keeps every
  account, cluster and token and adds the five default rules.

## Upgrading

No manual steps. Two database migrations, both only adding: three columns for the
verification code, and the tables for certificates and scheduled jobs. Kubernetes: `helm upgrade … --version 0.10.0 --reuse-values`
adds the Ingress permission. Docker Compose: set `WATCHLOG_VERSION=0.10.0`, then
`docker compose pull && docker compose up -d`.

Agents: certificates and scheduled jobs need agent 0.10. Upgrade servers with the command under
the fleet's **Add servers** (or the `docker run` command); until then the tabs name the servers
whose agent is older. Agents older than 0.10 keep working as before.

See [Certificates and scheduled jobs](https://github.com/watchlog-light/watchlog/blob/v0.10.0/docs/site/certificates-and-jobs.md)
for what is read, what is sent, and what isn't covered.
