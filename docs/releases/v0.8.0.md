# WatchLog 0.8.0

What changed: **see what changed first in every Kubernetes and Docker incident.** Each metric WatchLog scores from its catalog learns its own usual week. When something breaks, one list shows everything that left its usual range, in the order it happened, with the probable cause underneath. Anomaly alerts say "unusual for a Tuesday at 14:00", with no threshold to write ([What changed](https://github.com/watchlog-light/watchlog/blob/v0.8.0/docs/site/what-changed.md)).

It is statistics only: the median and the spread (MAD) of each hour of the week, worked out inside WatchLog. No machine learning, nothing sent to an AI, nothing leaves WatchLog, and the same data always gives the same answer.

**What changed is part of WatchLog Cloud Pro** (and Enterprise), the Pro beta included. Cloud Free and self-hosted Community see an upgrade page in its place, and nothing else changes for them: monitoring, alerts, the service map, probable cause and Egress watch stay free on every plan.

## What's new

- **How the usual range is learned** (ADR-196): for each scored series, the median and MAD of its one-minute values in each of the week's 168 hours (UTC), over the last 14 days, with a floor on the spread per kind of metric so a flat series doesn't make every wobble unusual. A series is used once it has 7 days of data. Minutes when another alert was firing on the same workload, Compose service or container are left out, so an incident doesn't become the usual. **Unusual** is a score over 4 for 10 minutes in a row; the usual range shown is the median ± 2 spreads.
- **The metrics it scores:** on Kubernetes, nodes and workloads (CPU, memory, network, disk), the requests, errors and p95 response time each workload serves, the service map's connections and HTTP between workloads, and the monitored applications' rates, latencies, connections, lag and queue depth; on Docker, the same for hosts and containers (named by their Compose project and service). Pods are not scored (they come and go; their workload carries them), nor are keys a default rule already covers as an event (restarts, OOM kills, conditions, throttling). Three catalog keys are new for both platforms: `workload.http.requests.rate`, `workload.http.errors.ratio` and `workload.http.latency.p95`.
- **The What changed page** (ADR-199), in the navigation of every cluster and fleet: windows around an alert, the last hour, the last 6 hours or a custom range of up to 24 hours; a chart of how many series were unusual each minute; ranked rows (when it started, what, usual → now, with a bar for how far out) by "first to move" or "furthest out"; and the probable cause card underneath, with its evidence, "Copy as text" and "Ask your AI". The list is ordered by time only: it doesn't link changes to each other.
  - **Kubernetes:** namespaces, workloads, nodes, the service map's edges and monitored services.
  - **Docker:** hosts, containers with their Compose project and service, edges and monitored services.
- **"What changed around it" on every alert:** the first three rows around the alert and a link to the page around it.
- **Anomaly alerts** (ADR-200): a default rule, **Unusual for this hour** (warning), added to Pro organizations by itself. One alert per subject and metric; quiet for 30 minutes after a rollout or image change of the workload (Docker: a re-created container, an image or Compose change); no anomaly alert while another alert is already firing on the same subject. The message says what, where and since when, "usual for Tuesday 14:00 UTC: 120–180 ms; now 2.4 s", and the likely cause when there is one, in email, Slack, Telegram and webhooks. The alert's page shows the series against its usual band and **"Was this worth an alert?"**: "No, this is normal for us" (Owners and Admins, audited, undoable) widens that series' range for that hour of the week, so the same value no longer alerts while a larger change still does.
- **The upgrade page** (ADR-201) for Cloud Free and Community: the live demo's example, labelled as the demo; your own last alerts with "What changed: Pro"; the price; "Upgrade to Pro" for an Owner on Cloud Free (or "Ask an Owner"), "Try WatchLog Cloud" on Community. Nothing on it calls Cloud from a self-hosted install.
- **API and MCP** (ADR-202): `GET /api/v1/what-changed` (a window or `alert=`, at most 24 hours and 50 rows), readable with an API token; MCP `get_what_changed` (30 rows, 16 KB), Kubernetes and Docker vocabularies, names returned as data only. Cloud Free gets 403 `pro-feature` and an in-band refusal from the tool; in Community the route answers 404 and the tool isn't registered, so Community's MCP tool list is unchanged.
- **The live demo** shows What changed: in demo mode the installation's organization has What changed (nothing else of Pro), and the demo learns from the 7 days of history it keeps at its first start, so its page has rows the day it is deployed (ADR-203).
- **Cloud:** the new tables are under Row-Level Security, and every new route and the MCP tool are in the cross-organization isolation suite (ADR-202).

## Where it runs

What changed needs a third process, the **anomaly-worker** (ADR-197), from the same backend image: `node dist/anomaly-worker.js`. It starts only in WatchLog Cloud (`WATCHLOG_EDITION=cloud`) or in the live demo (`WATCHLOG_DEMO_MODE=true`); anywhere else it prints why and exits. It scores only the clusters of organizations with Pro, never Cloud Free's.

- **Self-hosted (Community):** nothing to run. The Docker `compose.yaml` is unchanged, and the Helm chart's new `anomalyWorker` value is off.
- **The Helm chart:** `anomalyWorker.enabled` (default `false`; requests 50m CPU and 128Mi, memory limit 512Mi), for the live demo, which installs the public chart with `demoMode`: `--set anomalyWorker.enabled=true --set demoMode=true`. Without Cloud or demo mode the pod would only exit.
- **WatchLog Cloud** runs it as one more container with its own memory and CPU limits, measured with the load test's 1,000 nodes.

**`WATCHLOG_ANOMALY_ALERT_KEYS`** (on the alert worker; Cloud and the demo) chooses which metrics may raise an anomaly alert: a comma-separated list with `*` as a wildcard and `!` to leave out. Empty or unset is the default, `*,!edge.*`: everything but the service map's connections, which the page and the alert card still list. For example `workload.*,container.*,node.*,host.*` alerts only on workloads, containers, nodes and hosts.

## Upgrading

No manual steps (ADR-107, ADR-204). Kubernetes: `helm upgrade … --version 0.8.0 --reuse-values`; the new `anomalyWorker` value is read nil-safe, so values from 0.7.x render exactly what they rendered before. Docker: set `WATCHLOG_VERSION=0.8.0`, then `docker compose pull && docker compose up -d` for the server. Agents don't change: every 0.7.x agent and integrations collector keeps working, and the new keys come from the series agents already send.

**Learning starts at the upgrade.** In Cloud, each Pro organization starts learning the first minute the anomaly-worker sees it: at the 0.8.0 deploy for organizations already on Pro or the Pro beta, at the switch to Pro for the rest. Baselines read only data from then on, never the history before it, even where the plan keeps 30 days. Until 7 days have passed, the page, the alert card and the API say "Learning … until <date>", list nothing, and no anomaly alert is raised. A cluster or series that first reports later starts when it first reports. The live demo is the one exception (above). A downgrade stops scoring at once and keeps the baselines for 30 days, so an upgrade back within them resumes.

**Migrations run by themselves.** There are two, both forward-only; what each does to a self-hosted database:

- **What changed's tables** (`1795800000000_anomaly-baselines`): three new, empty tables, `anomaly_orgs` (when an organization started learning), `anomaly_baselines` (one row per scored series: the 168 hourly medians and spreads) and `anomaly_periods` (the unusual periods the page lists), each with its organization, a foreign key to its cluster and Row-Level Security, as every tenant table. Only the anomaly-worker writes them, so on a self-hosted install they stay empty.
- **Anomaly alert feedback** (`1795900000000_anomaly-feedback`): one new, empty table, `anomaly_feedback` ("Was this worth an alert?", under Row-Level Security); a column `plan_paused` on alert rules (false for every existing rule), so a downgrade can pause the anomaly rule and Pro again resume it; and two audit kinds, the answer given and undone. No existing row is rewritten.

The anomaly rule is added only to organizations with What changed, by the alert worker's default-rule upkeep; nothing is added to the rules of Cloud Free or Community. A server you upgrade keeps everything it had.

## Known limits

- **Pro only,** in WatchLog Cloud and the live demo. No self-hosted install runs it in 0.8.0 (self-hosted Enterprise gets it with the licence key later).
- **10 minutes:** a change that stays past a score of 4 for less than 10 minutes isn't listed. The score (4) and the minutes (10) are fixed; there is no sensitivity setting yet.
- **Not correlation:** the list is ordered by time; no rule draws a cause from which change came first or links changes across the service map.
- **UTC hours:** a daylight-saving change moves a local pattern by an hour for up to two weeks.
- **The HTTP keys** are seen from the caller's side, plain-text HTTP/1.x only, as on the service map.
- Windows are at most 24 hours; unusual periods are kept for your plan's history. No maintenance windows.
- English only.
