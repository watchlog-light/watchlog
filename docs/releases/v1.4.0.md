# WatchLog 1.4.0: MongoDB and Redis, much deeper

The MongoDB and Redis pages now answer what a person on call asks: **what is it waiting on,
what is responsible, which service sends it, and what changed**, on Kubernetes clusters and
Linux servers alike, with the same least-privilege users, read-only and never reading your
data.

## What's new

- **MongoDB, what it waits on.** Active operations sampled every 15 seconds by what they wait
  on (running, a lock, a ticket, flow control), by operation shape and by client. Shapes come
  from `$queryStats` where the server keeps it, otherwise from the slow log, with calls, mean
  against usual, documents examined against returned, **"sent mostly by"** and **"probably
  missing an index"** naming the collection and the fields it filters on.
- **MongoDB, the rest of the server.** Clients and their churn, open transactions and who holds
  them, idle cursors that never time out; each member's heartbeat, priority and votes, elections
  with why, rollbacks and flow control; collections' sizes, growth and reusable space; indexes
  unused on every member and redundant ones; eviction by application threads and checkpoints.
  A page for one shape and one collection.
- **Redis and Valkey, what fills the memory.** A bounded sample of key names (at most 20,000
  every 10 minutes, stopped if Redis slows) gives each prefix's memory, keys, share with a TTL,
  type and growth, and the largest keys. Values are never read; key names leave the collector
  only if you turn **Show key names** on.
- **Redis, the rest.** The main thread's share of a core; each command's calls, latency
  percentiles (7.0+) and failures; the slow log by the workload that sent each entry; clients
  against their output-buffer limits; **streams** and their consumer groups (lag, pending, the
  consumer that went quiet); whether the next save fits in the memory left; the backlog;
  Sentinel's masters and a cluster's slots. Pages for one prefix, command and stream group.
- **Findings with the cause first**, after the designs: "collection scans on shop.events, sent
  by analytics, fill the cache"; "keys under session:\* hold 58% of memory and 92% have no TTL:
  keys are being evicted"; "the main thread is saturated: KEYS, sent by report-cron"; "group
  billing is falling behind: its consumer is gone". Probable cause follows them to the workload.
- **Seven new default alerts**, few and precise; services monitored before are offered them on
  their Alerts tab.
- **Managed services** (Atlas, DocumentDB, ElastiCache, MemoryDB, Upstash) keep working; a
  panel whose command the server doesn't have says "not available on this server".

## Upgrading

Nothing to do; no migration. Update the integrations collector with the rest (the Helm chart and
the server install do). The generated Redis ACL names more commands, all read-only; a user
created before keeps working, and each panel it can't fill names the command to add. MongoDB
needs nothing beyond `clusterMonitor`. Details: ADR-247, ADR-248 and ADR-249, and the
[MongoDB](https://watchlog.io/docs/integrations/mongodb/) and
[Redis](https://watchlog.io/docs/integrations/redis/) pages.
